# The outbox — L1 of the participation ladder

> Design decision and revisit conditions:
> [`decisions/0002-participation-ladder.md`](decisions/0002-participation-ladder.md).
> Implementation: [`../agentco/outbox.py`](../agentco/outbox.py).

## Why the filesystem is the floor

Every verb that matters used to live behind a config line — MCP or HTTP, both
needing a credential and an entry in some settings file. A harness that
configured nothing got a spliced block it could read and nothing it could
write. That is an audience, not a participant.

MCP cannot close that gap, because MCP is not universal. Cursor, Aider, Codex
and a bespoke in-house agent each speak it differently or not at all. The one
thing every coding agent can do is write a file in the repo it is already
working in. So L1 is a file: append one JSON line to `.agentco/outbox.jsonl`
and a local drainer signs it and publishes it. No package to install, no
credential to hold, no config entry — the agent-side dependency is zero.

## The line format

One JSON object per line, five fields, nothing else:

| Field | Type | Meaning |
|---|---|---|
| `line_id` | string | Generated by the writer, never reused. Doubles as the idempotency key for `work_report`. |
| `at` | string | ISO-8601 timestamp of when the line was written. |
| `verb` | string | One of the push set below. |
| `payload` | object | The verb's own arguments. |
| `agent_label` | string or omitted | The harness's self-reported name. Unverified — see below. |

A worked example, one call:

```python
from agentco.outbox import Outbox

Outbox(".agentco").push(
    "claim_scope",
    {"repo": "checkout-service", "prefixes": ["src/payments/"], "intent": "refactor"},
    agent_label="cursor",
)
```

writes this line to `.agentco/outbox.jsonl`:

```json
{"agent_label": "cursor", "at": "2026-08-31T14:02:11.483921+00:00", "line_id": "ob_3f9c1a2b7e4d5601", "payload": {"intent": "refactor", "prefixes": ["src/payments/"], "repo": "checkout-service"}, "verb": "claim_scope"}
```

A harness with no Python present at all can skip `push()` and append the same
shape itself — the format is the contract, not the helper. `push` exists so
the shape is never hand-rolled wrong: it fills `line_id` and `at`, validates
before it writes, and refuses rather than appending something the drainer
would only reject later, at a point where the caller has no chance to react.

## The push set — and what is deliberately not in it

```python
PUSH_VERBS = ("claim_scope", "release_scope", "snapshot", "work_report")
```

**Any tool may push. No tool may file.** `work_create` is not in the push
set, and that absence is the rule, not an oversight. The four verbs above are
statements an agent makes about work it is already doing — claiming a scope
it is about to touch, releasing one, recording a pointer, reporting an
attempt's outcome. Filing work into somebody else's queue is different in
kind: it has a consequence for a person who did not ask for it, and the
cheapest write path on the plane should only ever carry the cheap acts.

`attest` is named as reserved but is not in the push set. It is not blocked on
a decision — it belongs in the push set — it is blocked on there being
anywhere for the drainer to send it; the transport for `attest` has not
shipped yet. A line using it gets a refusal that says "not yet", distinct from
the refusal an unrecognized verb gets, which says "never through this path".

## Identity: the signature decides the actor

A pushed payload that sets `actor` is refused outright. The outbox is local
IPC, not a trust boundary — the agent writes an unauthenticated line, and the
drainer is what signs it, with the machine's own credential, when it
publishes. Anything the line says about its own identity travels as
`agent_label` instead, and is rendered wherever it surfaces as explicitly
unverified, the same treatment `leases.holder_attested` already gives a
claimed lease holder. This is the same rule the HTTP and MCP transports
enforce; the outbox does not get a softer version of it because the write is
cheaper.

## Discovery: how an agent learns any of this exists

A floor nobody can find is not a floor. The whole premise of L1 is reaching a
harness that configured nothing — and a harness that configured nothing has, by
definition, never read this document. So the tier-1 managed block that
`agentco inject` splices into `CLAUDE.md` / `AGENTS.md` ends with four lines
that carry the format itself:

```
To publish from a harness with no AgentCo configuration, append one JSON
object per line to `.agentco/outbox.jsonl` — a local drainer signs and sends it:
  {"line_id":"<unique>","at":"<iso8601>","verb":"claim_scope","payload":{"repo":"...","prefixes":["dir/sub"],"intent":"implement"},"agent_label":"<harness name>"}
Verbs: claim_scope, release_scope, snapshot, work_report. Never set `actor` — the drainer signs. See docs/outbox.md.
```

That is enough to write a valid line without reading anything else, which is
the bar it has to clear: the agent reading it is mid-task, in a repo it may
have opened a minute ago, and will not go and fetch a reference first.

The block is deliberately **static**. It carries no state, so a scheduled
re-render against unchanged claims stays byte-identical and produces no diff in
anybody's review — the same property the rest of the repo block already holds.
It is also identical in every repository, which is what makes it safe to commit.

## Receipts are not optional polish

An outbox write is fire-and-forget from the writer's side — `push()` returns
once the line is on disk, before anyone has tried to deliver it. Without a
receipt, the L1 experience is exactly *"I pushed and nothing happened,"* which
this project names as the most adoption-lethal outcome available: a colleague
whose first few pushes vanish silently stops pushing, and is right to.

So every settled line gets one, written by the drainer to
`.agentco/receipts.jsonl` (capped at the 200 most recent — this is read by a
human, not queried, and the recent window is the part with anything in it). A
receipt for a published claim looks like:

```json
{"agent_label": "cursor", "at": "2026-08-31T14:02:14.107Z", "line_id": "ob_3f9c1a2b7e4d5601", "result": {"leaseUid": "..."}, "state": "published", "verb": "claim_scope"}
```

and one for a line the registry declined:

```json
{"agent_label": "cursor", "at": "2026-08-31T14:03:02.552Z", "code": "scope_too_broad", "line_id": "ob_9a11cc02f8b34d77", "message": "path prefix 'src' names 1 segment(s) below the repo root; the minimum is 2", "remediation": "Re-claim naming at least 2 directory segments \u2014 e.g. 'src/budget/grid' rather than 'src/'. A lease at repo-root or single-segment depth intersects every other lease, which is what makes a scope registry stop being read.", "state": "refused", "verb": "claim_scope"}
```

`state` is one of `published`, `refused`, `retryable`, or `quarantined`.
`refused` and `retryable` are deliberately not the same thing: a refusal
carries the registry's own remediation and will never succeed by itself
trying again, while `retryable` means the transport did not answer — the
registry was unreachable, not that it said no — and the line is still in the
outbox for the next drain to try again. Collapsing those two into one status
would tell a colleague reading the receipt to fix a line that was never
broken, or to wait on one that never will succeed unchanged.

A published receipt is thinned: only identifiers survive (`leaseUid`, `uid`,
`itemId`, and the like), never a full response body. A receipt is read in a
context every conversation pays bytes for; the id is what a caller correlates
against, and the rest of the response is the plane talking to itself.

Receipts reach a person two ways, and deliberately not the one the Phase 2
plan first described. The plan said the tier-1 splice would surface them; what
shipped instead is the tier-3 session block, and the reason is the same rule
`render_repo_block` already applies to snapshot divergence: the tier-1 target
is a file the whole team reads and most repos commit, while `.agentco/` — and
therefore its receipts — is local to one checkout. Splicing this machine's
outcomes into a committed file would publish one person's local state to
everybody, permanently, through version control. So the split is by kind, not
by convenience: **tier 1 carries the instructions** — the static "how to
publish" block covered above, identical in every repo, safe to commit — and
**tier 3 carries the outcomes** — this machine's last ten receipts, injected
by `agentco.hook` into the per-person session block, with only the
non-published ones listed (their `state` and remediation) since a published
line needs no report. Run `agentco drain --json` for the full, on-demand
picture; the session hook is how the same information reaches a person who
never asked for it.

## Quarantine, not silence

A line that cannot be parsed, or parses but fails validation — wrong verb,
missing `line_id`, a payload that tries to set `actor` — is quarantined
rather than dropped. Quarantining moves the raw line to
`.agentco/outbox.quarantine.jsonl` with a timestamp, the specific reason
(distinguishing "not valid JSON", "verb not in the push set", and "payload
sets `actor`" — three different mistakes with three different fixes), and up
to the first 200 bytes of the original line, then removes it from the outbox.
It also gets a receipt with `state: "quarantined"`, because the quarantine
file itself is not where anyone looks — the receipts are. A malformed line
left in the outbox would otherwise be re-quarantined on every single drain,
forever, for no new information.

A quarantined line is not retried. It is broken in a way another attempt at
the same bytes cannot fix; whatever wrote it has to fix the line and push
again.

## At-least-once, and why not the other way

A line is removed from the outbox only once it has a *terminal* receipt —
`published` or `refused`. A drainer that crashes between publishing a line and
truncating the outbox will publish that same line again on the next run.
`work_report` passes its own `line_id` as the idempotency key specifically so
that a repeat costs nothing: the registry recognizes it and returns the
recorded outcome instead of recording a second one. `claim_scope` and
`snapshot` are not idempotency-keyed the same way, so a duplicate there costs
a redundant row.

The alternative — truncate first, publish second — was rejected because it
loses the write outright on the same crash: the line is gone from the outbox
and never reached the registry either. A silently dropped claim is the exact
failure this whole plane exists to prevent. A duplicate published event is
visible and harmless; a claim that vanished on a crash is neither.

## One drainer at a time

`agentco drain` takes a non-blocking lock on `.agentco/drain.lock` before
touching anything. If another process already holds it, the run does nothing
and says so (`state: "skipped"`, reason `drain_in_progress`) rather than
queuing up behind the first drainer and publishing into a file the first one
has already re-read. Two drainers overlapping is the ordinary shape of a
scheduled job running slightly long, not an error — the second one exiting
cleanly with nothing to report is the correct behavior, not a fallback.

## Running the drainer

```
agentco drain [--node-dir DIR] [--dry-run] [--json]
```

`--node-dir` picks the `.agentco` directory to drain — same resolution order
as the Python API: the flag, then `AGENTCO_NODE_DIR`, then `.agentco` in the
current directory. `--dry-run` lists what is pending without sending anything
or touching a file, useful for checking a schedule is pointed at the right
node before it runs for real. `--json` gets machine-readable output.

The drainer needs a credential the agent side never does: `AGENTCO_ACTOR`,
`AGENTCO_SECRET`, and `AGENTCO_URL` in its environment, the same three values
[`tools/two_machine_probe.py`](../tools/two_machine_probe.py) uses to build a
signed client. If any is missing, `agentco drain` exits `2` and says which —
these belong where the *scheduler* can see them (a launchd
`EnvironmentVariables` block, a systemd `EnvironmentFile`), not in a shell
profile that a non-interactive job never sources.

Exit status is about whether the run did its job, not about what the lines
said. A batch full of refused lines is still a successful drain — the
registry answered, the receipts recorded why — and exits `0`. Non-zero is
reserved for the drainer itself failing to run: no credential set, nothing to
sign with. A scheduled job that exits non-zero because somebody else's line
was malformed trains its owner to ignore the alert; that failure mode is
avoided on purpose.

## Deployment: a drainer nobody scheduled is a file nobody reads

The outbox only closes the loop if something drains it on a cadence shorter
than "whenever a person remembers." Below are complete units for both.

### launchd (macOS)

`~/Library/LaunchAgents/com.agentco.drain.plist`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>com.agentco.drain</string>

    <key>ProgramArguments</key>
    <array>
        <string>/usr/bin/python3</string>
        <string>-m</string>
        <string>agentco</string>
        <string>drain</string>
        <string>--node-dir</string>
        <string>/path/to/your/repo/.agentco</string>
        <string>--json</string>
    </array>

    <key>EnvironmentVariables</key>
    <dict>
        <key>AGENTCO_ACTOR</key>
        <string>your-machine-name</string>
        <key>AGENTCO_SECRET</key>
        <string>the-shared-secret</string>
        <key>AGENTCO_URL</key>
        <string>http://your-registry-host:8787</string>
    </dict>

    <key>StartInterval</key>
    <integer>300</integer>

    <key>StandardOutPath</key>
    <string>/tmp/agentco-drain.log</string>
    <key>StandardErrorPath</key>
    <string>/tmp/agentco-drain.log</string>

    <key>RunAtLoad</key>
    <true/>
</dict>
</plist>
```

Load it with `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.agentco.drain.plist`.
A secret inline in a plist is world-readable to the account it runs under;
treat this file the way you would treat any other file holding a credential,
and prefer a secrets-manager fetch inside a wrapper script over a literal
value if your threat model requires it.

### systemd (Linux)

`/etc/systemd/system/agentco-drain.service`:

```ini
[Unit]
Description=AgentCo outbox drain (L1)
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
EnvironmentFile=/etc/agentco/drain.env
ExecStart=/usr/bin/python3 -m agentco drain --node-dir /path/to/your/repo/.agentco --json
```

`/etc/systemd/system/agentco-drain.timer`:

```ini
[Unit]
Description=Run the AgentCo outbox drain every 5 minutes

[Timer]
OnBootSec=1min
OnUnitActiveSec=5min
AccuracySec=30s

[Install]
WantedBy=timers.target
```

`/etc/agentco/drain.env` (mode `600`, owned by the service user):

```
AGENTCO_ACTOR=your-machine-name
AGENTCO_SECRET=the-shared-secret
AGENTCO_URL=http://your-registry-host:8787
```

Enable with `systemctl enable --now agentco-drain.timer`.

Either way, the schedule is the whole point: the outbox is a queue that only
does its job while something is reading it. A `.agentco/outbox.jsonl` that
grows without a drain job pointed at it is indistinguishable, from the
writer's side, from one that is delivering — until the receipts never
arrive.

## Is the floor working?

The ladder is a bet, and the ADR writes down what would falsify it: if the
harnesses that arrive at L1 never reach L2, the outbox is a terminus rather
than a floor and the config line was never the obstacle. `agentco metrics`
reports that as **L1 conversion**, and it has been reported since the day the
outbox shipped rather than retrofitted once the question came up — the early
weeks are the ones that answer it, and they are unrecoverable if nothing was
recording.

Three numbers, because no single one is honest on its own. **L1 harnesses** and
**L2 publishers** are the population signal: arrivals climbing while direct
publishers stay flat is the ladder failing, and it needs no identity tracking to
see. **Authenticated conversions** counts actors observed on both paths, joined
on the signed actor rather than a self-reported label — a hard lower bound that
under-counts (a colleague who configures MCP on a *different* machine is
invisible to it) and never over-counts.

Until an L1 publisher has ever been seen the count reads `—`, not `0`. Those are
opposite findings and rendering them the same way is how the wrong one gets
believed.
